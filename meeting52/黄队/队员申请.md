## 逐人说明

### Y1 · `yellow-meter`（测量复核员）— P0

- **职责**：只读，不改任何件；按 `R1_立场.md` §12.1–§12.4 的脚本复跑四类基线：
  1. 进程 RSS / `peak_wset`（bare / +numpy / +torch / +cuda）；
  2. `nvidia-smi` 整卡 vs `max_memory_allocated` 的差额（上下文归因）；
  3. 千层 D=64 / D=256 每拍墙钟（交替采样、5 批中位）；
  4. V4 贯通 D=256 全链路峰值。
- **为什么需要**：`R1_立场.md` 的 256 MB / 384 MiB 紧线**完全依赖** 180.2 MB 与 142–168 MiB 两个锚点；同进程自测有偏差风险，须换一个新进程、在空闲窗口复现。
- **产出**：`黄队/复核_基线.md`，含：每项 ≥5 次重复的 median/p95/max、与 R1 的偏差百分比、**偏差 >20% 的项标红并给重算后的阈值**。
- **边界**：只读；不跑会写 JSON 的判据脚本（`判据_千层骨架.py` 等）；不写 `黄队/` 以外任何路径。
- **验收**：复核表四类齐全 + 偏差表 + 对紧线的明确"维持/修订"结论。

### Y2 · `yellow-auditor`（预算审计员）— P1

- **职责**：对 `R1_立场.md` §3.2 分项表逐行审计，重点五类红队攻击面：
  1. **漏项**：工具子进程、两趟缓冲、码本、上下文、峰值碎片、解释器/numpy；
  2. **设计值冒充实测**：逐个核对每个数字的标注与来源；
  3. **均值掩盖峰值**：核对是否所有结论都用了峰值；
  4. **CPU/显存混用**：核对四列分法；
  5. **外部件排除**：RVC/桌面/浏览器是否被悄悄抹掉。
- **为什么需要**：分项表是 Round 2 裁决的算力依据，错一项即"算得起/算不起"判错。
- **产出**：`黄队/预算审计.md`，每行给 `原文数值 → 复算 → PASS/存疑/错 + 理由`；对"错"项给修正值。
- **边界**：只读既有件与 `黄队/R1_立场.md`；不改 R1（修正写进审计件，由队长 Round 2 合并）。
- **验收**：§3.2 全行覆盖 + ≥1 条实质发现（可为"未发现错，但 X 项缺来源"）。

### Y3 · `yellow-matrix`（矩阵成本核算员）— P1

- **职责**：把 `R1_立场.md` §4/§5 的成本公式做成**可复算表单**：
  - 输入：臂数、拍/臂、两趟、H 分布、D、单拍实测；
  - 输出：总墙钟、存储、**给定预算反解最大臂数 / H_max**；
  - 对 §7 降级阶梯每一级给"省多少 → 判据影响"的量化行。
- **为什么需要**：Round 2 各队会提新机制与新矩阵，逐次手算易错；需一个能按预算反解的工具表。
- **产出**：`黄队/矩阵成本模型.md`（公式 + 参数表 + 反解示例 + 敏感度：单拍 ±50% 时结论是否翻转）。
- **边界**：只读；纯纸面/脚本计算，不跑判据（避免写 JSON）。
- **验收**：反解表覆盖 D=64/D=256 × 30/60/120/240 min 四档；与 R1 §4.2/§5.2 数值一致（不一致须说明）。
