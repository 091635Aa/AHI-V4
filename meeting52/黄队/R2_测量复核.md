## 0. 结论（先给主控/队长）

1. **180.2 MB 峰值可复现**：我两次独立进程测得 **179.2 / 179.9 MiB**（差 −0.55% / −0.17%），口径为 `peak_wset`（OS 进程峰值工作集，含解释器+numpy）。**但 R1 的 D 标签错了：该实测跑的是 D=1024，不是 D=256**（默认全链路 `D默认=1024`，`桥.探针.shape=(16,1024)`，盘上 `判据_V4_贯通结果.json` 亦记 `"D":1024`）。显式 `造双区室(D=256)` 对照峰值 **178.7 MiB**，与 180.2 差 −0.8%，故**峰值量级不受影响，标签须改**。
2. **180.2 MB 不含 `import torch`、不含 CUDA 上下文**：该进程 `sys.modules` 无 torch/cupy/cuda，`nvidia-smi` 整卡 used 运行前后不变（135→135 MiB）。它是**纯 CPU RSS**。同进程同时 `import torch` + 跑全链路，峰值 **654.7 MiB**（[复测]）。
3. **"均值 111.4 MB" 是口径错误**：我复测的**跑完 RSS = 111.5 / 111.9 MiB**（与 111.4 吻合到 0.1–0.5 MB），而 10 ms RSS 采样的**均值 = 132.9 / 137.5、中位 = 148.8 / 150.4、p95 = 170.1 / 170.2 MiB**。111.4 只能解释为"末态 RSS"，**不是时间均值**，也不符合 R1 自己 §3.1 P2 的"取采样中位数"定义。
4. **引擎本体 16.29 MB 漏账约 1/3**：D=256 全数组 nbytes 合计 **23.98 MiB（25.15 MB）**；R1 的同口径子集=16.26 MiB（16.29 对得上），漏掉 **`最近快/最近输出/最近汇` 三块 U×D scratch = 7.594 MiB**＋读出/归一 0.094＋其他 0.029。D=64 同病：R1 4.141→实测 6.104 MiB。
5. **`import torch` +475.4 MB 与 CUDA 上下文 142–168 MiB 复现**（+474.9 MiB；+142 MiB init、释放张量后净 +168 MiB；`max_memory_allocated` 零张量报 **0.0** 而整卡已 +142 MiB——漏账成立）。**但 host 侧 cuda.init 成本 R1 记 +20.8 MB 系少计**：那只是 `is_available()` 步；CUDA 真正就绪（`synchronize` 后）host RSS +103.3 MB（502.3→605.6）。
6. **计时类数字全部受并发支配**：D=64 14.58 ms 我复测 15.56/16.33 ms（+7%/+12%，仍在 R1 自报 13.3–18.0 内）；**D=256 75.42 ms 不是可复现单点**（最优一轮 96.0 ms、min 66.6；其余三轮 200.4/220.5/383.6 ms；H=3 并发下单样本最坏 990 ms）。抓屏 30.5–44.8 ms 是 **mss 降级路径**（与盘上旧 mss 预检同量级，[文献类比]；红队 R2 并发测 46.9–84.3 ms 同量级），**现行眼睛走桌面复制连续流：取帧 1.5 µs、新帧处理 4.7 ms/帧（盘上预检）**；nvidia-smi 61–117 ms 复现（安静 61.2–82.6）。
7. **6.6 MB → 4.428 MB 的更正成立**，并给出算式与根因（§2.2）：6.6 是**规格设计式** `U·D·(1+m)` 的值；实现容器参数只有 1.107 M。两数都只是 [设计值]，**且"定点存储"当前并未打包**（数组实测 float64，参数实占 8.492 MiB）。
8. **与 R1 勘误横幅的关系**：R1 已自加 R2 勘误（引擎 16.29→24.13、scratch +35.22、C1=D1024、256→320 MB、两趟 +24.13、18 臂 59.6 min）。我**独立复测证实**其中与测量相关的 4 项（D=1024、引擎 ~24 MB、scratch 由同队审计补、峰值 180 可复现），并**补 4 项勘误未覆盖的**：①"均值 111.4"是末态 RSS；②抓屏 30–45 ms 走的是 mss 降级路径；③"torch 常驻 Σ 518.8"应为 654.7；④**CUDA host 成本 +103.3 MB**（R1 记 +20.8，只到 `is_available` 步）。

> **最不可信的数字**：① **"均值 111.4 MB"**（口径错、且末态 RSS 本身不稳定，D=256 对照跑到 170.4 MiB）；② **"每拍 D=256 75.42 ms"**（并发下 96–990 ms，不能作 T3/T5 拍预算的单点锚）。若只挑一个：**"均值 111.4"**——它被当成"均值"写进结论，实际三者都不是（非均值、非峰值、非稳定量）。

## 2. 关键差异的展开（为什么错、错多少）

### 2.1 "D=256 全链路"标签错（结构性错误，影响引用）

- `贯通_多核心.py:32`：`D默认 = 1024`；`_引擎维(桥)` 取 `桥.探针.shape[1]`，实测 `(16, 1024)` ⇒ **默认全链路 D=1024**。
- 盘上既有结果 `meeting49/实施/判据_V4_贯通结果.json` 的实测摘要含 `"D": 1024`（自模型迹→D=1024）。
- 显式 `造双区室(D=256)` 可跑（1 拍与 120 拍均无异常），但**桥内部仍是 1024**；其峰值 **178.7 MiB**、墙钟 12.81 s（120 拍 ⇒ ≈9.4 拍/s），说明 180 MB 主要由六内核桥决定、对"D"不敏感。
- **建议表述**：`V4 贯通链（六内核宿主，母语维 D=1024；显式 D=256 对照 178.7 MiB）峰值 180 MiB`。不要把 180.2 写成"D=256 全链路"。

### 2.2 6.6 MB 与 4.43 MB 的算式（结论：6.6 是别的公式）

（1）**证据 §4 那行**：`定点存储 1.11 MB（D=64，int32×4B）`，同行又写 `设计值 D=256 时约 6.6 MB`。按同一行自己的线性外推：

```
D=64 :  摘要参数总量 276,736 × 4 B = 1,106,944 B = 1.107 MB(10⁶) = 1.056 MiB
D=256:  摘要参数总量 1,106,944 × 4 B = 4,427,776 B = 4.428 MB(10⁶) = 4.223 MiB
        即 1.107 MB × (256/64) = 4.428 MB            ← 与 R1 的 4.428 一致
```

（2）**6.6 MB 是哪来的**：`规格_千层张量_四轴.md:131` 的设计式 `参数量 = U·D·(1+m)`，取 U=1296、D=256、m=4：

```
1296 × 256 × (1+4) = 1,658,880 参数
1,658,880 × 4 B = 6,635,520 B = 6.636 MB(10⁶) ≈ 6.6 MB
```

规格件 `:178` 明写"1.66 M 参数 / 6.6 MB / 每拍 1.66 M 乘加均为**设计值**"。而**实现容器**的参数是 `U·D + 4·D + W_in + W_in全`（`W_in全` 为 `U·D×输入维`，输入维=2），D=256 实测 **1,106,944**，即实现的参数化是"**边类权重共享（4×D）＋W_in全**"，不是规格里的"逐单元 4 条入边向量（m·D）"。所以：

- **6.6 与 4.43 相差 1.499×，是两个不同公式，不是同一行的笔误**；
- 证据 §4 的问题是把 **D=64 的实测（1.11 MB）与 D=256 的设计式（6.6 MB）混写在同一行**；
- 若要保留设计式，应写"规格设计式 6.6 MB；当前实现（参数共享）4.43 MB，二者不可互换"；
- **且两者都只是 [设计值]**：int32 打包未实现，实测数组 float64，参数实占 **8.492 MiB**；`参数总量()` 含读出/偏置/P_入（1,119,256 ⇒ 4.477 MB），`摘要()` 不含（1,106,944 ⇒ 4.428 MB），引用须说明用哪一个。

### 2.3 "均值 111.4" 不是均值

| 量 | 值（两次独立进程） | 说明 |
|---|---|---|
| 末态 RSS（跑完 120 拍后） | 111.5 / 111.9 MiB | 与 R1 的 111.4 吻合；但它是**一个时间点**，且随变体变化（显式 D=256 对照跑到 **170.4**） |
| 10 ms 采样 mean | 132.9 / 137.5 MiB | 时间加权；随运行时长变化（29.5 s vs 44.8 s 两轮不同） |
| 采样 median / p95 | 148.8 / 170.1、150.4 / 170.2 MiB | R1 的 P2 说"取采样中位数"⇒ 按协议应报 ≈149，不是 111.4 |
| 峰值 `peak_wset` | 179.2 / 179.9 MiB | 与采样 max 178.1 / 179.0 吻合（采样捕到峰值 99.4% / 99.5%） |

⇒ **建议**：删除"均值 RSS 111.4 MB"这一表述，改为「跑完 RSS 111.4 MB；运行期采样 mean/median/p95 = 133/149/170 MB；峰值 180 MB」。否则"均值掩盖峰值"的反向错误（用一个末态点冒充均值）会被红队直接咬住。

### 2.4 引擎 16.29 MB 漏账明细（D=256，nbytes）

| 类 | MiB | 备注 |
|---|---|---|
| 1 参数（g/边权/W_in/W_in全/P_入） | 8.492 | R1 记 8.49 ✓ |
| 2 状态（A慢/B快/输出） | 7.594 | R1 记 7.59 ✓ |
| **3 最近 scratch（最近快/最近输出/最近汇）** | **7.594** | **R1 全漏**（各 2.531） |
| 4 读出/归一（读出/读出偏/均/方） | 0.094 | R1 部分未列 |
| 5 记忆容器 | 0.020 | R1 记 0.11（含读出/归一，合并了） |
| 6 拓扑/索引 | 0.157 | R1 记 0.08（D=64 值，D=256 另有轴向量） |
| 7 其他（pro/外单元/层槽等） | 0.029 | — |
| **合计** | **23.980（25.145 MB）** | R1 同口径子集 16.263（其表 16.289） |

> 结论：**16.29 → 应为 23.98 MiB**（若坚持"只算参数+双态"则应写 16.26 MiB 并注明不含 scratch）。另：`最近快/输出/汇` 是每拍要用的常驻缓冲，不是临时量，必须入账。
> 补充（同队审计 T-c，本会话未复跑）：千层 D=256 **单拍 scratch 峰值 +35.22 MB**（RSS 2 ms 采样，300 拍）——这正是"nbytes 24 MiB"与"运行峰值"之间的瞬态部分，**峰值账必须单列 scratch，不能拿 nbytes 当峰值**。

### 2.5 抓屏：R1 用错了路径（对 T5 影响最大）

- `器官_眼._截屏()` 的**首选**是 `连续采集`（Windows 桌面复制 DDA）：后台线程取最新帧槽，`取()`≈**1.5 µs**（我实测 30 次 median 1.5 µs、p95 1.7 µs），新帧处理按盘上预检 **4.7 ms/帧**（`连续采集.py` 文件头，[文献类比]）；我实测静屏新帧 11–13 帧/s，帧龄 5–52 ms，`起()` 9.7 ms、`预热()` 585.6 ms（一次性）。
- `mss` 单帧只是**降级路径**（流不可用/帧过旧 >3 s 才走）。R1 引用的 30.5–44.8 ms 与盘上旧 mss 预检（`步0_基线台账.md:248`、`连续采集.py:4`，30–45 ms/拍）同量级；R1 未给该值的采样协议，无法判定是本会话实测还是引用旧件，但它测的是 **mss 降级路径**，不是现行主路径。
- **对 T5 的影响**：R1 §6.1 用"观测 30.5–44.8 ms"推出"D=256 闭环 111–140 ms > 100 ms/拍"。按现行连续采集，"观测"在拍内≈帧龄读取（µs 级）+ 后台 4.7 ms/帧（不在拍内）⇒ 拍内预算应重算为 **决策 75–96 ms＋动作注入（未测）**，而不是 111–140。结论不宜写成"打穿"或"能塞进"的任一端，应写成"**边界不确定：取决于决策实测中位（75 vs 96 ms）与键鼠注入延迟（未测）**"。

## 3. 测量协议（可复跑 · 黄队冻结提案）

> 目标：换人或换天复跑，数字能落在同一区间；**每个数都带"工具 + 口径 + n + 并发状态"**。

### CP0 · 环境快照（每次测量前必记）

```powershell
Get-CimInstance Win32_Processor | Select LoadPercentage,CurrentClockSpeed,MaxClockSpeed,NumberOfLogicalProcessors
Get-Process python -ErrorAction SilentlyContinue | Select Id,CPU,@{n='RSS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
Get-CimInstance Win32_OperatingSystem | Select TotalVisibleMemorySize,FreePhysicalMemory
nvidia-smi --query-gpu=memory.used,memory.free --format=csv,noheader
```
- 记录项：时间、CPU 负载%、CPU 频率、空闲内存、**其它 python 进程数/RSS**、整卡 used。
- **硬要求**：任何计时数字必须与"并发状态"同表；并发 >30% 时**不得**报单点墙钟。

### CP1 · 峰值定义（三层，不许混）

| 层 | 工具 | 用法 | 本机实测表现 |
|---|---|---|---|
| **主口径** `peak_wset` | `psutil.Process().memory_info().peak_wset` | OS 峰值工作集；自本进程启动累计（含解释器/导入）；不含子进程 | 179.2/179.9（n=2，差 0.7 MiB） |
| 辅口径 采样 max | 10 ms 请求采 `rss` | 交叉核对；采样线程 daemon；**报实测频率** | 实际 57–64 Hz；采样 max 178.1/179.0，捕峰 99.4%/99.5% |
| 均值 | 同上序列 | 必须报 **mean + median + p95 + 窗口**；`mean` 依赖运行时长，只作参考 | mean 132.9/137.5，median 148.8/150.4，p95 170.1/170.2 |
| **禁止** | — | 把"跑完 RSS"叫"均值"；把 CPU RSS 说成显存；用单次 `rss_after` 代替峰值 | — |

- **全链路**＝主进程 `peak_wset`；有子进程时＝同一时刻 Σ(rss) 再对时间取 max，主/子分列；外部件（桌面合成器、浏览器、RVC）单列声明，**不相加、不抹掉**。
- 显存四分法（沿用 R1 §3.1 P3）：CPU-常驻 / CPU-峰值 / DEV-分配器 `max_memory_allocated` / DEV-整卡 `nvidia-smi` 增量；**DEV 两列并列，永不相加**。

### CP2 · 采样

- RSS 采样间隔 **10 ms 请求**（psutil `memory_info().rss`），**必须报实测 Hz**（本机 GIL 下 ≈57–64 Hz）；采样线程开销 <1%。
- 窗口：预热后（前 20% 拍）→ 结束；同时给全窗与后 80% 窗两套统计。
- CUDA：`nvidia-smi` 采样间隔 **≥200 ms**（单次 61–117 ms，不能进热路径）；基线每次先测、**只报 delta**（本轮基线 135→136 MiB，R1 时 54 MiB，delta 一致）。

### CP3 · 重复次数与报告量

| 对象 | 最小重复 | 报告 | 本机依据 |
|---|---|---|---|
| 内存峰值 | **≥3 次独立进程**（peak_wset 方差小，≥2 可验 ±1 MiB） | median + max + 全部原值 | 179.2/179.9（2 次已差 0.7 MiB；本轮因时间窗只做 2 次，建议 3） |
| 墙钟/每拍 | **≥5 次独立进程 × 每进程 ≥5 rep × 每 rep 10 拍**，GC 关闭、5 拍预热 | **min / median / p95 + 并发负载 + CPU 时间** | D=256 单点 75.42 在 4 轮里跨 96–383 ms；只有 min/区间可用 |
| 抓屏 | ≥10 次 | median / p95；分 mss 与连续采集两行 | mss 20.7（安静）/80.4（并发）；DDA 取帧 1.5 µs |
| nvidia-smi | ≥10 次 | median / p95 | 74.3（安静）/156.7（并发） |
| 两趟一致性 | 每臂 2 趟 | 状态指纹逐位（C13）；**内存不要求**逐位 | 沿用 R1 P2/P4，本轮未跑 |

### CP4 · 计时口径

- 双记：`time.perf_counter()`（墙钟）**与** `time.process_time()`（本进程 CPU 时间）；两者都报。
- 本机实测 **wall/CPU ≈1.00–1.03** ⇒ 千层单拍是单线程；但 CPU 时间也会因**频率/缓存被并发挤压**而涨（我测到 D=64 CPU 中位 32.8 ms vs 安静期 15.6 ms）⇒ **CPU 时间不是"免并发"的救命指标，仍须记录负载**。
- 交替 D/H 顺序采样；报 `H3/H1` 时同时报 F/R 拟合值并注明"两点拟合，受噪声放大，不作独立结论"（R1 的 F/R 与我的拟合差异大：D=64 F 6.06/9.46 vs 7.74，R 8.52/6.87 vs 13.49，**不建议把 F/R 写进结论**）。

### CP5 · 抓屏双路径（T5 预算必须两行）

| 路径 | 测什么 | 本轮实测 |
|---|---|---|
| **连续采集（现行主路径）** | `预热()` 一次性；`起()`；`取()` 成本；新帧率/帧龄；单帧处理成本（盘上预检 4.7 ms） | 预热 585.6 ms、起 9.7 ms、取 1.5 µs、静屏 11–13 帧/s、帧龄 5–52 ms |
| mss（降级路径） | 单次 `grab` + `np.asarray`/`cvtColor` | 20.72 ms（安静）/ 80.4 ms（并发）；转换 0.38–0.65 ms |
| 记录-重放存储 | 帧字节数（RGB=3B/px、BGRA=4B/px） | 1920×1080 RGB＝6,220,800 B＝5.933 MiB；90 帧/3 s＝534 MiB（[复测-算式]） |

### CP6 · 单位与标注纪律

- 内存：**MiB（二进制）+ MB(10⁶) 双列**；显存 MiB；时间 ms/s。禁止一行内混用（R1 的 5.93 MiB / 8.29 MB 行即为反例）。
- 标注：`[实测]/[复测]/[设计值]/[文献类比]/[未验证假设]`；**空着＝未测**；设计值不写成实测（R1 的 4.428/6.6 均属设计值）。
- 每个数必须能由 §9 的命令复跑；不能复跑的数必须写清"哪台机器、哪天、谁跑的"。

- **证据**：§1 复核表（逐行给出 R1 值/复测值/差异/原因）、§2 展开、§9 探针脚本与原始输出；关键源件：`贯通_多核心.py:32`、`判据_V4_贯通结果.json`（`"D":1024`）、`算子_千层骨.py:154-264/772`、`规格_千层张量_四轴.md:131/178`、`连续采集.py:1-23`、`器官_眼.py:114-139`。
- **反证（什么能推翻我）**：
  1. 若在**无并发空闲机**上 ≥5 次独立进程测得 D=256 单拍 median ≤80 ms，且 `peak_wset` 稳定在 180±2 MiB，则计时部分维持 R1 原值（我的 96 ms 判为并发伪影）；
  2. 若同一 `runpy` 脚本再跑 3 次 `peak_wset` 均 >185 或 <175 MiB，则我的 179.2/179.9 也须重测（当前 n=2）；
  3. 若 R1 能给出 111.4 的采样序列（而非末态 RSS），则"均值口径错"撤回；我要求附 n/间隔/窗口；
