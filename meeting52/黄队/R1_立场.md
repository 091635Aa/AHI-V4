## 0. 一句话立场

**"更小显存"目前不是可测命题，"≤1GB / ≤2GB"两条线又太松、不具区分力。**
黄队实测：本机纯 numpy 全链路（六内核 × 两区室，D=256，120 拍）**峰值 180.2 MB / 均值 111.4 MB**；引擎本体（千层，D=256）**构造占用 16.29 MB**；而 `import torch` 一项就 **+475.4 MB**、CUDA 上下文再 **142–168 MiB 显存**。⇒ 1GB 红线有 **5.7× 余量、必然通过**，不能当"成就线"；要判"更小"必须补 **CPU ≤256 MB 峰值 / GPU ≤384 MiB 峰值** 两条紧线。**"比某基线省"类命题一律否**——盘上不存在同功能的对照实现，无基线即不可测（对应简报 A3）。

### 1.3 引擎本体（千层，`算子_千层骨.py`，按 §12 脚本构造后量 `nbytes`）[实测-构造]

| 项 | D=64（行为探针） | **D=256（设计值）** |
|---|---|---|
| 参数总量（`参数总量()`） | 279,832 | **1,119,256** |
| 容器参数（`摘要()["参数总量"]`） | 276,736 | **1,106,944** |
| 参数数组 float64 实占 | 2.12 MB | **8.49 MB** |
| 状态 A慢/B快/输出 float64 | 1.90 MB | **7.59 MB**（各 2.531） |

| **引擎常驻合计（float64）** | **4.141 MB** | **16.289 MB** |

> **两条必须分开的账**：
> ① 「定点」是**数值精度策略**（值量化到 2^-20 格），数组 dtype 实测仍是 **float64**；不额外打包成 int32 就**不省内存**。证据 §4 的 1.11 MB 是"若打包"的理论值，不是常驻值。

### 1.4 每拍墙钟（单进程、进程内交替采样、GC 关闭、5 warmup + 5×20 拍取中位）[实测]

| 配置 | H=1（环路 1 轮） | H=3（环路 3 轮） | H=3/H=1 |
|---|---|---|---|
| **D=64** | **14.58 ms**（13.3–18.0） | **31.62 ms**（28.8–37.1） | 2.17 |
| **D=256** | **75.42 ms**（65.0–99.9） | **150.55 ms**（130.1–204.2） | 2.00 |

> 交叉校验：证据 §4 的「21 臂 ≈ 8 分钟」⇒ 22.9 s/臂 ÷ 14.58 ms ≈ **1,570 拍/臂**，与「训 900 + 测 300 + 预热/额外」量级吻合。**这验证了本节墙钟锚点可用于后续预算。**

## 3. T2 · 资源账战（**本队核心**）

### 3.1 基线测量协议（可复跑；四段式）

#### 协议 P1 · 常量基线（解释器 / 运行时 / 上下文）

```
阶段 0  空进程            → 读 RSS、peak_wset
阶段 1  import numpy      → 读 RSS（增量 = numpy 成本）
阶段 2  import torch      → 读 RSS、记导入耗时
阶段 3  torch.cuda.init() → 读 RSS（host 侧）+ nvidia-smi 整卡 used（device 侧上下文）
阶段 4  alloc 256 MiB 张量 → max_memory_allocated + nvidia-smi；释放后 empty_cache()
```
- **每个阶段必须分进程、单会话、串行**（阶段 3 的 host RSS 与 device used 不得混算）。
- 阶段 3/4 的 `nvidia-smi used` 减阶段 0 的桌面基线（本机 54 MiB）= **进程整卡占用**；再减 `max_memory_allocated` = **上下文+缓存+他进程**。
- **禁止**：拿 `max_memory_allocated` 当整卡占用（B2 实测差 142–168 MiB）；拿 RSS 当显存。

#### 协议 P2 · 常驻/峰值采样（全链路运行期）

| 参数 | 取值 | 依据 |
|---|---|---|
| RSS 采样间隔 | **10 ms**（psutil `memory_info().rss`） | 单次读取微秒级，扰动可忽略 [实测] |
| 峰值来源 | **`peak_wset`（OS 级，无需采样）** + 采样序列 max 交叉核对 | 本机 psutil 支持 [实测] |
| nvidia-smi 采样间隔 | **≥ 200 ms** | 单次查询 **61–117 ms** [实测]，采样必须远慢于被测事件 |
| 均值窗口 | 预热后（前 20% 拍）→ 结束；取采样中位数 | 排除冷启动/导入 |
| 重复次数 | **≥5 次独立进程**；报 **median / p95 / max** | 本机 ±20–50% 波动 [实测] |
| 两趟一致性 | **新进程各跑一次同种子**；比**状态指纹逐位同**（C13） | 功能必须逐位同；**内存不要求逐位同**（分配器非确定），只要求两趟 median 差 ≤10% |
| 线程/进程边界 | 主进程 + **所有**子进程；同一时刻取 Σ，再对时间取 max | 漏子进程＝漏账（红队攻击面） |

#### 协议 P3 · CPU 内存 vs 设备显存（四分法，强制分列）

| 列 | 仪器 | 含义 | 本机锚点 |
|---|---|---|---|
| CPU-常驻 | psutil RSS | 主进程主机内存（含解释器/numpy/CUDA host 侧） | §1.1 |
| CPU-峰值 | psutil `peak_wset` | 主进程 OS 峰值 | §1.5 |
| DEV-分配器 | `torch.cuda.max_memory_allocated()` | **仅本进程 torch 张量**；零张量时报 0 | B2 |
| DEV-整卡 | `nvidia-smi --query-gpu=memory.used` 增量 | 含上下文+缓存+**其他进程**；WDDM 无法按进程归因 | B1–B4 |

- **全链路 = CPU-峰值（Σ主/子进程）+ DEV-整卡**，两列**不相加**、并列报。
- 外部件（RVC 8 GB 占位、浏览器、桌面合成器 54 MiB）**必须声明**：可排除在"AHI 自有"外，但不得从"整卡"里悄悄抹掉。
- 纯 numpy 引擎的 DEV 应为 **0**；实测本机当前引擎即 0（全程 CPU）。若某方案上 GPU，DEV 从 142 MiB 上下文起跳。

#### 协议 P4 · 两趟缓冲（C13 口径）

- **顺序两趟（推荐）**：同一进程跑两遍或两进程各一遍，只留**指纹 16–32 B**；内存不翻倍，墙钟 **×2.0**。
- **并行两趟**：同时保留两套状态用于逐位比对 ⇒ 内存 **+16.29 MB**（D=256 引擎）。**本队不推荐**：为省 16 MB 不值得翻倍峰值。
- 含外部工具时：**实时两趟不可能逐位同**；必须「固定输入流 / 记录-重放」（见 §6），且**帧存储要计入账**。

| 65,536 | 1024 | fp16 | **128 MB** | fp16 实测 2.3× 省带宽/显存 [文献类比] |

### 3.3 阈值提案（含"为什么是这个数"）

| 层 | 指标 | 提案阈值 | 依据 | 判定含义 |
|---|---|---|---|---|
| **L0 红线**（所有者 Q2） | CPU 常驻（全链路） | **≤ 1 GB** | 简报 §6 Q2 | 通过与否，**不是**成就 |
| **L0 红线**（若上 GPU） | 设备显存峰值 | **≤ 2 GB** | 简报 §6 Q2 | 同上 |
| **L1 紧线**（黄队） | CPU 峰值 `peak_wset` | **≤ 256 MB** | C1 **180.2** + 工具子进程 **16.1** + 屏幕 **5.93** = 202.2；×1.25 安全 = **253 → 256** | 判"更小"的真判据 |
| **L1 紧线**（黄队） | CPU 均值 | **≤ 128 MB** | C1 均值 111.4 ×1.15 | 抓"均值掩盖峰值"的反面 |
| **L1 紧线**（若上 GPU） | `max_memory_allocated` 峰值 | **≤ 384 MiB** | 上下文 142–168 + 引擎 16.3 + 两趟 16.3 + scratch ≈64 = 238–265；×1.5 = 357–397 → **384** | 判"显存是否真小" |
| **L1 紧线**（若上 GPU） | `nvidia-smi` 整卡增量 | **≤ 384 MiB** | 同上，防上下文漏账 | 与分配器并列 |
| **L2 零线** | 纯 numpy、DEV=0 | 当前引擎**已满足** | §1.5 | 作为回归守卫 |

**"为什么 1GB 不是可判命题"（三段论）**
1. 实测全链路峰值 **180.2 MB = 1GB 的 17.6%**；引擎本体 **16.29 MB = 1.6%**。
2. 1GB 的 47.5% 被 `import torch` 一项吃掉（502.4 MB）——**阈值实际在判"你选了什么运行时"，不在判"模型/机制大小"**。
3. 因此：**纯 numpy 方案 5.7× 余量通过、任何模型改动都几乎不影响结论** ⇒ 红线只防"灾难"（如 torch 多子进程、RVC 共存），**不能用来声称"更小"**。要判"更小"，用 L1 紧线（256 MB / 384 MiB）。

**"更小显存"相对什么？——否**
- 盘上**没有**同功能的第二实现（无 torch/GPU 版七项子集）。没有对照基线 ⇒ **"比 X 省"不可测**。
- 唯一可测句：**"在 ≤256 MB CPU 峰值 / ≤384 MiB 显存峰值下，七项子集各有消融与失败对照"**（与简报 A3 一致）。
- 本队**拒绝**任何"比 MOSS 省 / 比基线省"的表述进入方案（无基线）。

### 3.4 四件套（T2）

- **主张**：Q2 的 1GB/2GB 在本机**必然通过、不具区分力**；必须冻结 **L1 紧线（CPU 峰值 ≤256 MB / 均值 ≤128 MB；GPU 峰值 ≤384 MiB）**，且"更小"只能表述为绝对上界、不能表述为相对基线。
- **证据**：§1 全部锚点 + §3.2 分项加总 + §3.3 三段论。
- **反证（须失败对照）**：① 在**空闲机**复跑 P1–P2，若 C1 峰值 >256 MB（如迹加长到 1000 拍），紧线须上调并重算；② 任何方案若引入 torch 常驻，L1 必然 FAIL（502.4 MB）——**这是预期的"必须失败"臂**；③ 若只报 `max_memory_allocated` 而 `nvidia-smi` 差 >200 MiB，判该报告无效（漏上下文）。
- **算力代价**：协议本身开销——5 次重复 × (P1 约 15 s + P2 按被测臂墙钟) + nvidia-smi ≥200 ms 间隔；单方案基线复测 **≈5–10 min/轮**。[推算]

### 3.5 T2 的"算不起"判定线（直接否）

| 方案特征 | 判定 | 依据 |
|---|---|---|
| torch 常驻 + ≥2 个 torch 工具子进程 | **否**（1GB 爆） | 502.4×2 = 1,004.8 MB，已超 1GB |
| 单码本 M=65,536×D=1,024 fp32（256 MB）于 256 MB 紧线 | **否** | 单件吃满紧线 |
| 记录-重放存原始帧（3 s） | **否**（534 MB） | §6 |
| 无对照基线的"更小"宣称 | **否**（不可测） | §3.3 |

## 4. T3 · 联合消融矩阵战：代价与"算不起时的最小可判子集"

### 4.1 成本公式

```
单臂拍数 T_arm ≈ 1,500（训 900 + 测 300 + 预热/额外；由 21 臂 8 min 反推 [实测]）
单臂墙钟  = T_arm × 单拍(H, D) × 两趟(2)
矩阵总墙钟 = 臂数 × 单臂墙钟 + 进程启动(numpy 0.22 s/进程)

D=64  H=1 : 1,500 × 14.58 ms  = 21.9 s/臂/趟
D=256 H=1 : 1,500 × 75.42 ms  = 113.1 s/臂/趟
```
> 每臂若含"拆后 + 续训回升"（戊2 口径），另加 ≈600 拍（复苏）；下表按**含复苏 +600 拍**折算约 ×1.4。

### 4.2 矩阵规模 vs 墙钟（D=64，两趟）

| 矩阵形态 | 臂数 | 单趟 | **两趟（C13）** | D=256 两趟 [推算] |
|---|---|---|---|---|
| 基线 + 7 单点消融 | 8 | 2.9 min | **5.8 min** | 30 min |
| + 5 个高风险双拆（最小子集，见 §4.3） | 18 | 6.6 min | **13.2 min** | 69 min |
| **全部两两 2×2（21 对 ×3 + 基线 + 7 单点）** | **71** | 25.9 min | **51.8 min** | **4.5 h** |
| **全因子 2⁷** | **128** | 46.7 min | **93.4 min** | **8.1 h** |

> 含复苏 ×1.4 后：71 臂 ≈ **73 min**（D=64）/ **6.3 h**（D=256）；128 臂 ≈ **2.2 h**（D=64）/ **11.3 h**（D=256）。

### 4.3 最小可判子集（算不起全矩阵时）

**基线 1 + 7 单点 + 5 高风险双拆 + 3 sham + 2 迁移 = 18 臂**
- 高风险对（按简报 §3 耦合箭头）：**P1 自模型×记忆、P2 自模型×潜在推理、P3 记忆×潜在推理、P4 潜在推理×工具闭环、P5 provenance×自模型**。
- 其余 **16 对登记为"未测"**，不得默认为"可分离"。
- 成本：**13.2 min（D=64 两趟）**，含复苏 ≈ **18 min**；D=256 ≈ **92 min**。[推算]
- **必须失败对照**：每对双拆须同时给「A 单拆、B 单拆、A+B 双拆」三格；缺一格则该对不计入归因（防单点消融伪归因——千层戊2 教训）。

### 4.4 四件套（T3）

- **主张**：全两两矩阵（71 臂）在 D=64 单会话可跑（≈52 min 两趟），**全因子 2⁷ 在 D=256 算不起（≈11 h）**；因此矩阵必须降为 18 臂最小可判子集 + 显式列出 16 对未测。
- **证据**：§1.4 墙钟 × §4.1 公式 × §4.2 表；21 臂 8 min 交叉校验。
- **反证（须失败对照）**：① 单点消融必须给"拆后反升"登记（轴C 型）与"拆后不回升"（轴D 型）两种失败模式；② 若把 18 臂实测墙钟 >2× 估计，则最小子集也不可跑，须再降（§7 L1/L2）。
- **算力代价**：§4.2 表；存储：结果 JSON ≈0.7 KB/臂（18 臂 < 15 KB），**潜伏态日志若全开 1.8 MB/臂 ⇒ 71 臂 = 128 MB，须只对 2–3 个因果臂开**。

## 5. T4 · 潜在循环：拍数代价与"难度→步数"可行区间

### 5.1 代价模型（实测拟合）

```
单拍墙钟(D,H) = F(D) + R(D)·H
D=64 : 6.06 + 8.52·H   ms
D=256: 37.85 + 37.57·H ms
两趟 ×2；单臂 1,500 拍
```
[实测] H=3/H=1 = 2.17（D=64）、2.00（D=256）——**环路成本亚线性**（固定项 F 占大头）。

### 5.2 可行区间（约束：21 臂 × 1,500 拍 × 两趟）

| 单次会话预算 | D=64 允许 H̄ | D=256 允许 H̄ |
|---|---|---|
| ≤30 min | **H̄ ≤ 1.8**（H≤2） | **不可行**（H=1 已需 79 min） |
| ≤60 min | **H̄ ≤ 4.0**（H≤4） | 不可行 |
| ≤120 min | **H̄ ≤ 8.7**（H≤8） | **H ≤ 1** |
| ≤240 min | H≤16+ | H ≤ 3.2（H≤3） |

> 关键数：D=64 每加一轮环路 **+8.52 ms**（单趟）；D=256 **+37.57 ms**。**"难度→步数"自适应调度在 D=256 下没有预算空间**（H=1 已 79 min/21 臂），只能在 D=64 行为探针上判。

### 5.3 四件套（T4）

- **主张**：潜在循环的"难度→步数"调度**只能在 D=64 探针上判**：预算 ≤120 min 时 H_max≈8（H̄≤4 时 ≈33 min）；**D=256 只能固定 H=1**（≈79 min），多步须 4 h 级。
- **证据**：§5.1 拟合 + §5.2 表。
- **反证（须失败对照）**：① **H=0/H=1 必须给出掉分**（否则循环是装饰）；② 若实测 H=3 相对 H=1 的墙钟比 >2.5×（当前 2.0–2.17），则每轮成本 R 被低估，可行区间再收窄；③ 若调度只改步数不改输出（扰动潜在态无响应），该臂不计入（装饰性思考，T4 红队攻击面）。
- **算力代价**：见 §5.2；存储：潜伏态日志 1.8 MB/臂（D=256）——仅在因果干预臂开。

## 6. T5 · 工具调用闭环：延迟预算与外部依赖风险

### 6.1 延迟预算（每循环 = 观测 + 决策 + 动作）

| 组成 | D=64 | D=256 | 依据 |
|---|---|---|---|
| 观测（单次全屏抓取） | **30.5–44.8 ms** | 同左 | [实测] |
| 决策（一拍） | **14.58 ms** | **75.42 ms** | [实测] §1.4 |
| 动作（键鼠注入） | **5–20 ms [未验证假设]** | 同左 | 未测 |
| **单循环合计** | **50–80 ms** | **111–140 ms** | [推算] |
| AHI3 技能档实际节奏 | **100 ms/拍**（150/100/50/30 拍 = 15/10/5/3 s） | — | [文献类比 meeting41 证据_三层] |

> **结论**：**D=64 闭环可塞进 100 ms/拍（余量 20–50 ms）；D=256 打穿拍预算（111–140 ms > 100 ms）**。故 T5 的实时闭环臂必须跑 D=64，或把观测压到 ≤5 ms（差分抓屏/局部抓屏，**未测**），或把拍口径放宽到 200 ms（会改变 AHI3 技能档语义）。
> **注意**：`nvidia-smi` 的 61–117 ms 是**测量仪器成本**，不是工具延迟；采样不得置于闭环热路径内。

### 6.2 记录-重放的存储代价（C13 与外部世界相容的唯一路径之一）

| 方案 | 3 s episode 存储 | 判定 |
|---|---|---|
| 原始帧 1920×1080 RGB @30 fps | 5.93 MB × 90 = **534 MB** | **否**（>256 MB 紧线，逼近 1GB 红线） |
| PNG 压缩帧（≈0.5–1.5 MB/帧，[未验证假设]） | **45–135 MB** | 可行但吃紧 |
| 特征级/稀疏帧（未知压缩率） | [未测] | 需先测压缩率再定 |

> **本队判定**：若 T5 要求"C13 逐位同 + 真实工具"，**记录-重放原始帧不可行**；必须走「固定输入流（合成帧）」或「特征级重放」，并在方案里写明压缩率与存储预算。

- **主张**：工具闭环的**拍预算由观测决定**：全屏抓取 30–45 ms 使 D=256 决策（75 ms）无法塞进 AHI3 的 100 ms/拍；实时闭环只能用 D=64，且 C13 逐位同**只能靠固定输入流/特征级记录-重放**，原始帧重放 3 s = 534 MB **算不起**。
- **证据**：§6.1 表、§6.2 表、§6.3 清单；C3/C4 实测。
- **反证（须失败对照）**：① 切断观测→行为退化（开环冒充闭环的阴性对照）必须 FAIL；② 若差分抓屏实测 >20 ms，则 D=256 闭环仍不可行；③ 若记录-重放两趟指纹不逐位同，则该路径无效。

## 7. 降级阶梯（超预算时的**有序**砍法）

排序原则：**先砍已被自己的证据否证/无增益的件 → 再砍需复验的数值项 → 最后砍规模/功能（改变宣称）**。每级给「省多少（实测/推算）→ 对判据的影响 → 必做复验」。

| 级 | 动作 | 省什么 | 对判据的影响 | 必做复验 | 标注 |
|---|---|---|---|---|---|
| **L1 离线账** | 重放/巩固移出在线峰值，单独分账 | 在线重放缓冲 + 32 拍/轮 墙钟 | **丙3 已 FAIL**（重放增益 +0.027）⇒ 无新增判据损失；C13 须声明"在线/离线分账" | 无（已有负结果） | [文献类比]/[实测] |
| **L2 分块** | 按层档激活，不整 U×D 常驻 | 峰值内存 ≈30–40%（16.3→~10 MB）；墙钟 +10–20% | 必须保持 **R2 拍内序贯**，否则甲2 更差（已 FAIL）；乙3 环路须复跑 | 甲2/乙3/丁1 | [设计值] |
| **L3 精度** | float64→float32（或 int32 打包） | 内存 ≈50%（16.3→8.2 MB）；墙钟约 1.5–2× 快 | **C13 风险最大**：2^-20 格在 float32 可表示，但累加序敏感 ⇒ 两趟须重验；ε_self 等阈值可能漂移 | V4 16 + 贯通 10 + 规则 8 + 千层 21 全复跑 | [文献类比 meeting38 E0] |
| **L4 稀疏** | m=4→2 或 top-k 更硬 | 汇计算 ≈50%、墙钟 ≈20–30%；**内存不省**（状态仍是 U×D） | 甲1/乙1/乙3/乙4 复跑；迁移可能掉 0.05–0.10 | 上列四臂 | [设计值] |
| **L5 U↓** | 层档 6→3、时档 6→3（U 1296→324） | 引擎内存/墙钟 **÷4** | **直接跌出"U≥1024 千层"口径**；但甲2 已证层档无独立收益 ⇒ 这是**承认丢千层**的最便宜方式 | 更新宣称口径 | [实测-甲2]/[设计值] |
| **L6 D↓** | D=256→64 | 墙钟 **÷5.2**（75.4→14.6 ms）、内存 **÷4** | 表达力/迁移下降；**行为判据本来就在 D=64** ⇒ 改为"行为判 D=64、计费 D=256"双口径 | 迁移臂 + 设计值声明 | [实测] |
| **L7 功能子集降级** | 七项合并/降为 5 项 | 线性 | **直接减少判据覆盖**；不得用于宣称达成 | 冻结槽位登记"未判子集" | [设计值] |

> **黄队执行建议**：超紧线 → L1（零判据损失）→ L2（若内存紧）→ L3（若墙钟紧，但代价最大）→ L4 → L5 → L6 → L7。
> **禁止**：用 L3 的"更快"去宣称"更小模型"；用 L5/L6 降级后仍按原设计值口径报墙钟/显存。

### 12.1 P1/P2 探针（基线 RSS / 峰值 / CUDA 上下文）

```python
# 用法：单进程串行跑四个阶段；每阶段读 psutil + nvidia-smi（外部）
import psutil, time, os
p = psutil.Process()
def snap(tag):
    mi = p.memory_info()
    print(tag, "rss_MB", round(mi.rss/1048576,1),
          "peak_wset_MB", round((getattr(mi,"peak_wset",0) or 0)/1048576,1))
snap("bare")
import numpy; snap("+numpy")
import torch; snap("+torch")
if torch.cuda.is_available():
    torch.cuda.init(); torch.cuda.synchronize()
    snap("+cuda_init")          # 同时外部跑 nvidia-smi --query-gpu=memory.used
    x = torch.zeros(256*1024*1024//4, dtype=torch.float32, device="cuda")
    torch.cuda.synchronize()
    print("max_allocated_MB", torch.cuda.max_memory_allocated()/1048576)  # 与 nvidia-smi 对照
    del x; torch.cuda.empty_cache(); snap("after")
```

## 13. 本队结论（给主控的 6 行）

1. **可测口径**：CPU RSS/peak_wset 与 DEV 分配器/整卡**四列分列**；`max_memory_allocated` 漏 142–168 MiB 上下文；WDDM 不可按进程归因。
2. **基线 [实测]**：全链路峰值 **180.2 MB**；引擎 D=256 **16.29 MB**；`import torch` **+475.4 MB**；CUDA 上下文 **142–168 MiB**。
3. **阈值**：1GB/2GB 是红线、**不具区分力**；冻结提案 = **CPU 峰值 256 MB / 均值 128 MB；GPU 峰值 384 MiB**。
4. **算得起**：七项单项判据（≈50 min/会话）、18 臂最小矩阵（≈18 min）、D=64 H≤8 潜在循环（≤78 min）。
5. **算不起（否）**：全因子 2⁷@D=256（≈11 h）、实时工具两趟逐位、torch 多子进程、原始帧记录-重放（534 MB）、无基线的"更小"宣称。
6. **降级顺序**：离线账 → 分块 → 精度 → 稀疏 → U↓ → D↓ → 功能子集；**精度降级对 C13 风险最大，必须全量复跑**。
