## 0. 一句话主张 + 四件套

**主张（可证伪）**：**黄队的资源数字复现得很好，但阈值不是判据**——同一份代码、同一次运行，只改「口径 / horizon / 采样窗口」这三个**未冻结**的参数，黄队四条线里**三条的结论翻转**：
① **1GB**：WS（工作集）口径 179.2 MB＝5.7× 余量 PASS；**commit（提交）口径 1252.2 MB＝1.22× 超支 FAIL**（同一进程、同一时刻，仅换仪器）；
② **256MB CPU 峰值**：120 拍 PASS（179.2，1.43×）；**2000 拍 FAIL（274.4 MB，实测）**；
③ **128MB CPU 均值**：黄队报 111.4；本轮按同一路径复跑 mean 147.2/156.8、median 156.3，按黄队 P2 的「预热后取采样中位数」推算约 **170 MB（[推算]，由 p95 172.0 与末值 171.3 支撑）⇒ FAIL**（且均值随墙钟/窗口 ±20–50% 不可复现）。
⇒ **T2 现状不是「超预算/不超预算」，而是「口径未冻结 ⇒ 不可裁决」**。正确动作不是接受任一条线，而是**先冻结四元组口径（metric, horizon, scope, threads/baseline），再按两条 horizon 判**，并把「测量无效」显式判 FAIL（见 §4.1）。

1. **证据**：§1.3 关键实测表（全部本轮 [实测]）+ 黄队 R1 锚点逐项复现；§2 漏项 L-01…L-16；§3 逐条对账；§6 翻转清单。
2. **反证（什么结果推翻我）**：在冻结口径（resident 峰值 / 递归进程树 / OPENBLAS_NUM_THREADS=1 固定 / GPU 每轮测基线 / horizon 2000 拍 / 5 次重复）下，五条线的判定**全部一致且两次重复差 ≤10%**，且**分项和与全链路峰值差 ≤10%** ⇒ 我方「不可裁决」主张被推翻，可直接采纳黄队阈值。任一条做不到 ⇒ 该条线仍不可判。
3. **必须失败对照**：§4.2 的 M-R01…M-R10（每条先登记预期值；「该失败却通过」＝仪器失效，不算方案通过）。
4. **算力代价**：本轮全部只读测量 **≈4 min 墙钟**（2000 拍贯通 88 s 为最大项，其余秒级）；冻结口径后的全量复测 **≈10–30 min/配置**（5 次重复 × (构建 10–17 s + 2000 拍 78–90 s) + GPU 上下文/子进程臂）。**2000 拍只要 90 s——「只测 120 拍」没有算力借口。**

## 1. 测量条件与关键实测

### 1.2 复跑方法（只读、不落盘）

- 内存：`ctypes` 调 `psapi.GetProcessMemoryInfo`（`PROCESS_MEMORY_COUNTERS_EX`）读 `WorkingSetSize / PeakWorkingSetSize / PagefileUsage / PrivateUsage`；与 `psutil.Process().memory_info()` 交叉核对（两路一致，见 §2 L-04）。
- 子进程：`subprocess.Popen([venv_python, "-B", "-c", code])`，子进程打印自身 `os.getpid()` 后再采样（**不能采 `Popen.pid`**，见 L-08）。
- GPU：外部 `nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits`；每点 3–5 次取众数/中位。
- 贯通：`sys.path.insert(0, r"...\meeting49\实施"); import 贯通_多核心 as g; 双=g.造双区室(); g.跑(双, N)`（全链路 = 六内核宿主 + 两区室核，`贯通_多核心.py:62-96`；**它是只读模块，运行不写文件**）。
- 采样：`threading.Thread` 每 10 ms 读一次 RSS；贯通跑 `g.跑` 期间采样（实际间隔 15.6–17.4 ms，见 L-11）。
- 未跑：`判据_*`（会写 JSON）、真机键鼠、RVC 并行、跨进程确定性臂。

## 3. 对黄队阈值/结论的逐条对账（R2 交叉攻击）

### 3.1 「1GB 有 5.7× 余量 ⇒ 不具区分力」——**一半成立，一半危险**

- **成立的一半**：数字对（我复现 5.71×）；且「1GB 实际在判运行时选择」——`import torch` 一项 475.5 MB＝1GB 的 46.4%，换运行时即翻。这一句应保留。
- **危险的一半**：**「不具区分力」只对「纯 numpy + 120 拍 + WS 口径」成立**。三个条件任一变化都翻：commit 口径（现系统已超 22%）、2000 拍（紧线 FAIL）、torch 常驻 / 2 个子进程（1GB 压线/超）。所以不能据此把 1GB 降级后**连口径也不冻结**——否则等于用最有利口径的 5.7× 余量掩盖另外两本账的超支。
- **建议措辞**（可写进方案）：「1GB/2GB 是**外部红线**（判运行时与子进程数量，不判机制大小）；机制大小由 **256/384 双 horizon 线 + commit 第二判据** 判；任何『更小』表述必须带四元组口径（§5）。」

### 3.2 紧线判据强度（256 / 128 / 384）

- **CPU 峰值 256MB**：强度＝**能判「有没有 torch / 有没有长跑 / horizon 多长」，不能判「模型多大」**。120 拍 1.43×、600 拍 1.23×、1200 拍 1.08×、2000 拍 0.93×。作为「更小」的判据，它实际测的是 **horizon**（crossover≈1500–1600 拍）。**要么把 horizon 写死为 ≤1200 且禁止长跑宣称，要么把线改成 384MB@2000 拍**（§5 提案）。
- **CPU 均值 128MB**：**强度 0**（不可复现、口径未定义、两次同配置差 6.5%，且我复测即 FAIL）。建议删除该线；若一定要「抓均值掩盖峰值」的反面，改成 **稳态中位数 ≤X 且 p99/peak 比 ≤1.2**（这测的是「尖峰陡不陡」，不测绝对大小）。
- **GPU 峰值 384MiB**：**校准按 1 个 CUDA 进程做的**，而 T5 的架构天然是多进程（工具子进程）。实测上下文 **142 MiB/进程**：N=1 可过；N=2 约 380（余量 1%）；N=3 必超。⇒ 384MiB 的真实语义是「**最多 1 个 CUDA 进程**」，必须在冻结槽位写死；否则任何 torch 工具子进程方案会在「看起来达标」的 384MiB 线下偷偷超支（或被误判）。
- **还要防「分配器口径」**：零张量 `max_alloc=0` 真实 196/278 MiB（L-02）；协议必须**同时**报 `nvidia-smi` 整卡增量与 `max_memory_allocated`，两者差 >50 MiB ⇒ 判该报告 VOID。

### 3.3 N3「2 个 torch 子进程 502.4×2 > 1GB」——**成立，我原本怀疑「共享 DLL 会少算」，实测否掉**

两个并发 torch 子进程：ΣRSS **1003.1 MB**，同时段系统物理可用降 **1003.5 MB**（差 0.4 MB）⇒ torch 的 475 MB 几乎全是私有常驻，**没有可观的共享页抵扣**；加上父进程/启动器，实际 >1.02 GB。**黄队的 must-fail 臂选对了**，唯一要补的是 L-08（必须按进程树采，否则采到启动器 4.5 MB 会假 PASS）。

### 3.4 「D=64 闭环可塞进 100ms（余量 20–50ms）」——**结论不翻，余量不成立**

抓屏实测 **46.9–84.3 ms**（黄队 30.5–44.8；本轮桌面有 QQ/GameViewer）+ D=64 决策 14.58 ms ⇒ 单循环 **61–99 ms**：**最坏余量 1.4 ms**，不是 20–50 ms。D=256（决策 75.4 ms）则 **122–160 ms，确定打穿**。⇒ T5 的闭环拍预算必须写成「观测 p95/p99 + 决策 + 动作」三列，不允许用单次均值；且 `nvidia-smi`（100–126 ms）**禁止进热路径**（黄队已写，我补实测值）。

### 3.5 全链路峰值 180.2MB 与「均值 111.4MB」——**一个可信，一个不可复现**

峰值：4 次复跑 179.2–181.0，**可信**（但仅 120 拍 horizon）。均值：按 P2 定义复算得不到 111.4；我的 mean 147.2/156.8、median 156.3、p95 172.0，后段中位≈170 [推算]。**「均值 ≤128MB」如果作为现系统的回归守卫，现状即 FAIL**；如果它是「未来优化目标」，必须标注「当前 147–170，未达标」，不能写成「PASS」。

### 3.6 分项表 vs C1：**分项表用的引擎不是全链路的引擎**

黄队 §3.2 Σ 行「纯 numpy 自有引擎（D=256）≈16.4 MB」，而 C1（`贯通_多核心.py`）是**六内核 × 两区室、D=1024**：我实测构建后 WS **117.3 MB**、commit **1109.2 MB**。分项 Σ 43.4（16.4+27）vs 峰值 180.2 ⇒ **76% 未归因**；即便补上 numpy 27 MB 也只到 43.4。按黄队 A2.3 自设「分项和与总峰值差 ≤10%」**不达标**。修正方向：分项表必须以 §5 的「全链路口径」重建（六内核 D=1024、含迹增长、含子进程树），否则「分项预算表」不能作为 pass/fail 依据。

## 4. must-fail 资源臂 + 「超预算怎么判 FAIL」

### 4.1 判定规则（先冻结，再判；任一「测量无效」＝FAIL，不得记 PASS）

| 规则 | 条件 | 判定 |
|---|---|---|
| **R-FAIL-1 超线即 FAIL** | 在声明口径/horizon 下，`peak_wset`（递归进程树同刻 Σ 的 max）> 声明线 | **FAIL**（不给「接近」档；余量必须 ≥1.1× 才算 PASS） |
| **R-FAIL-2 VOID 即 FAIL** | 任一子/孙进程未计入；用 `Popen.pid` 冒充进程；未报 horizon；未报口径；线程未冻结 | **VOID → FAIL**（不得记为「通过」） |
| **R-FAIL-3 漏账即 FAIL** | 分配器峰值与 nvidia-smi 整卡增量差 >50 MiB；或 commit 未报 | **VOID → FAIL** |
| **R-FAIL-4 不稳定即 FAIL** | 同配置同种子 5 次：峰值差 >10%，或均值/中位差 >20%；或换 `OPENBLAS_NUM_THREADS` 后判定变 | **FAIL**（判据不稳定＝无判据） |
| **R-FAIL-5 基线漂移即 FAIL** | GPU 判据未在每轮前后各测 3 次桌面基线（当前漂移 54→142 MiB） | **VOID → FAIL** |
| **R-FAIL-6 漂移率超限即 FAIL** | 2000 拍内峰值增长 >60 MB/1000 拍（当前实测 ≈50 MB/1000 拍，已临界） | **FAIL**（除非迹被 cap 并复测） |

## 5. 对「更小显存」可测定义的反建议（可直接冻结的文本）

> 前提：引擎纯 numpy、**DEV=0**（不初始化 CUDA）——此时「显存」不是引擎指标，「更小显存」对引擎无对象（与黄队/裁决 A2 一致）。**但「无对象」不等于「不可测」**：可测的是「**设备侧是否初始化、初始化了几个进程**」与「**宿主侧常驻**」两本账。盘上无同功能第二实现 ⇒ **一切「比 X 省」表述仍判不可测**。

### 5.1 冻结口径：五元组（缺一 → VOID）

```
资源声明 = (metric, horizon, scope, runtime_freeze, baseline)
  metric  ∈ {host_peak_wset, host_steady_median, host_commit_peak,
             dev_alloc_peak, dev_card_delta}          # 必须分列，禁互相代用
  horizon = (逻辑拍数 N, 墙钟, 重复次数)               # 例：N=2000, ≈90 s, 5 次
  scope   = 递归进程树（含启动器）；外部件（桌面/QQ/RVC）单列声明，不得悄悄抹掉
  runtime_freeze = {PYTHONHASHSEED, OPENBLAS_NUM_THREADS=1, OMP_NUM_THREADS=1, 单核?}
  baseline = GPU 桌面 used（每轮前后各 3 次，取中位）；RAM available
```

### 5.2 我主张的判据（替代 1GB/256MB/128MB/384MiB 四条单线）

| 判据 | 内容 | 为什么（本轮实测依据） |
|---|---|---|
| **P-R1 设备** | 纯 numpy 实现必须报 **N_cuda=0 且整卡增量 ≤0 MiB**（「无显存」是可证的好事）；若 N_cuda≥1，报 **N_cuda、整卡增量 ≤142×N + 128 MiB @2000 拍**；`max_memory_allocated` 只作下界，与整卡差 >50 MiB ⇒ VOID | 上下文 142/进程实测；allocator 零张量报 0；mem_get_info 盲 |
| **P-R2 宿主峰值** | **≤384 MB @2000 拍**（含 1 个工具子进程 + 观测帧；实测 274.4+52.3+5.93≈332，余量 1.16×）；若坚持 **256 MB**，则 horizon 必须写成 **≤1200 拍**（实测 236.4，余量 1.08×）且禁止「常驻 2000 拍」宣称 | 2000 拍 274.4；600 拍 207.9；工具子进程峰值 52.3 |
| **P-R3 稳定性** | 5 次同配置：**峰值差 ≤10%**；稳态中位差 ≤20%；否则 VOID。**删除「均值 ≤128MB」**（不可复现），改为「稳态中位数 + p99/peak ≤1.2」 | mean 147/157 不一致；median 156；p95 172 |
| **P-R4 漂移率** | 报告 **MB/1000 拍** 斜率，阈值 **≤60 MB/1000 拍**（当前 ≈50，已临界）；超限 ⇒ 必须 cap 迹（`内核_自我回路.迹` 环形上限，属既有件改动，需主控备份授权）或判 FAIL | 120→2000 拍 +95.2 MB（≈50.6 KB/拍）；迹 365→2245 无界 |
| **P-R5 范围** | 递归进程树；启动器与真解释器都算；外部件单列；GPU 每轮基线；线程冻结 | trampoline 4.5 vs 501.7；基线 54→142 |
| **P-R6 两趟** | 内存只单趟测（顺序两趟峰值只反映较大趟，L-14）；两趟只比**指纹**，不比内存 | `peak_wset` 单调；黄队 P2 已写「内存不要求逐位同」但未定判据 |

### 5.3 「更小」的替代表述（唯一可测句）

> **「在 (metric, N=2000 拍, 递归进程树, 线程冻结, 每轮基线) 下，配置 P 的五元组逐项严格小于配置 Q 的同五元组，且七项功能子集各有消融与 must-fail 对照。」**
> 禁止：「比 MOSS 省」「比基线省」「显存更小」（无对照实现 → 不可测，来源：裁决 A2 / 黄队 R1 §3.3）。
