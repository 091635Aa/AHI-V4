## —— N 倍扩展的「延迟-显存」代价曲线，与把代价压成非线性的逃逸路径

> 议题锁定（唯一）：**N 倍扩展的「延迟-显存」代价曲线究竟是什么？给定预算下可行的 N 上限是多少？如何把代价压成非线性？**
> 身份锚定：实时系统 / GPU 工程。只谈延迟、显存、带宽、吞吐；容量数学归 01 号专家。
> 纪律：本轮**不改任何既有文件**；本文所有新数字均为**本机实测**或**基于实测锚点的外推**（逐项标注）。
> 硬件口径：**RTX 3080 Laptop GPU（16GB）**，`torch 2.14.0+cu130`（`.venv` 实测可用），AHI 显存预算 **≤8GB**（RVC 可能独占 8GB），负载目标 GPU<5%、≥60FPS。
> 禁 Transformer 铁律遵守：本文全部算子为 HDC 双极超向量的按位乘 / 多数表决 / 点积，无 attention / QKV / softmax / 梯度。

## 0. 一句话结论（给所有者）

**悖论是真的，但不在你以为的地方。** 绑定位乘、多数表决、工作区读写全是 O(D) 且常数极小（微秒级，实测 0.005–0.25ms）——
**真正的成本几乎全部落在一件事上：余弦检索要扫过整个码本，代价 ≈ 码本码位数 M × 维度 D 的显存流量，即 O(M·D)，它随扩容线性长。**
所以"维度更多→思考更慢"的物理机制不是"算不动"，而是**每拍要把码本从显存搬一遍**（实测有效带宽 ≈ 310 GB/s）。
在"≤8GB + 思维拍 ≤50ms + 词表 M≥65536"下，**线性扩维的上限是 N=16（D=16384，单拍 13.9ms，码本 4GB）**；把词表压到 8192 码位可推到 **N=128（D=131072，13.9ms，4GB）**，但单 bundle 容量只到 ~6.5×10³，**仍差一档到 10⁴**。
**唯一能"容量↑而常驻延迟不变"的路是多分辨率按需展开（E5）**：常驻只扫粗码（D_c=1024，0.13ms，与细码分辨率完全无关），细码只在命中的 k 个候选上按需展开——实测带宽省 6.4×，这是把线性曲线掰弯的主路径。

| 查询摊销 Q | D=1024, M=8192 | Q=1:0.092｜8:0.119｜**32:0.124**｜128:0.279｜512:1.043｜1024:2.02 ms | 批量摊销锚点 |

### 1.2 关键观测：谁是瓶颈

1. **检索 = 码本读带宽瓶颈**。三档不同规模（256MB / 1GB / 32MB）给出同一有效带宽 **≈ 3.3 µs/MB → 310 GB/s**（3080 Laptop HBM 峰值的 ~70%）。→ 检索延迟严格 ∝ M·D。
2. **绑定 / 捆绑 / 工作区 = 与检索差 2–3 个数量级**。D=1024 时它们合计 ~0.03ms，检索 0.86ms。**扩维的"思考变慢"几乎 100% 来自检索。**
3. **查询批量近乎免费**：Q 从 1→32，总耗时仅 0.092→0.124ms（×1.35），**每查询代价降 24×**；Q>32 后转为算力瓶颈（Q=1024 时 2.02ms，反推 fp32 有效算力 ≈ 8.5 TFLOPS）。
4. **fp16 预转换 2.3× 加速**（0.870→0.378ms）：码本字节减半直接减半流量。**量化是零风险的免费扩容。**
5. **容量律实测确认**：单 bundle 保真 ≥0.99 的成员数 K ≤ **0.05–0.1·D**（D=1024→100、D=16384→800+）。与简报 §2 的"0.1·D"一致。**容量 ∝ D 线性。**

## 2. 代价模型（估公式，锚定实测）

### 2.1 符号

| 符号 | 含义 | 取值 |
|---|---|---|
| D | 超向量维度 = 1024·**N** | D∈{1024,2048,4096,8192,16384,…} |
| **N** | 扩维倍数（本文口径 = D/1024） | 1,2,4,8,16,… |
| M | 码本码位数（可寻址 cleanup 码数） | 设计量，本文取 8192 / 65536 |
| b | 每元素字节 | fp32=4, **fp16=2**, int8=1, 位打包=0.125 |
| Q | 单次检索的批量查询数 | ≤32 摊销区 |
| R | 单拍检索次数 | 1–4 |
| B | 单次算子批向量数 | 128 |
| K | 捆绑路数 / 候选数 | 8 / k |
| BW | 有效显存带宽（实测） | **3.1×10¹¹ B/s** |
| F | fp32 有效算力（实测） | **8.5×10¹² FLOP/s** |

### 2.2 四部分延迟公式（皆为估公式，丰度按实测比例）

```
绑定   T_bind   ≈ 3·B·D·b / BW          （读2写1；实测 D=1024,B=128 → 0.0049ms）
捆绑   T_bundle ≈ 3·K·B·D·b / BW        （K 路读+归约；实测 → 0.0242ms）
检索   T_retr   ≈ M·D·b / BW  +  2·M·D·Q / F
                 └─ 码本读（Q≤32 主导）    └─ Q>32 转算力瓶颈
工作区 T_ws     ≈ 3·S·D·b / BW          （S=槽数，单向量，微秒级）
单拍   T_tick   ≈ R·T_retr + T_bind + T_bundle + T_ws
```

**结论式**：`T_retr[ms] ≈ M·D·b / 3.1e8`，其余三项合计 `≈ D·4e-5 ms`（比检索小 3 个数量级）。

### 2.3 显存公式

```
码本    V_cb ≈ M·D·b                    （唯一主项）
工作区  V_ws ≈ S·D·b + 结构化字典       （≤1MB）
临时    V_tmp≈ Q·D·b + M·Q·4            （分数矩阵 (M,Q)，8MB@M=65536）
合计    V ≈ M·D·b + ~10MB
```

## 3. 【硬要求 1】代价曲线表：D ∈ {1024 … 16384}

> 基准配置：**M=65536 码位**（全模态词表，属简报 §2 的 10³~10⁴ 档）、Q=32、B=128、fp32。
> 「实测」= 本机基准；「外推」= 按 M·D 线性（由 256MB@3.35µs/MB 与 256MB@3.4µs/MB 两点锚定）。

| D (N) | 绑定 | 捆绑 | **余弦检索** | 工作区读写 | **单拍合计** | 码本显存 fp32 | 总计显存 | 单 bundle 容量(≥0.99) |
|---|---|---|---|---|---|---|---|---|
| 1024 (N=1) | 实测 0.0049 | 实测 0.0242 | **实测 0.858** | 实测 0.0040 | **≈0.89 ms** | 256 MB | ≈0.27 GB | ~100（0.98@100） |
| 2048 (N=2) | 实测 0.0062 | 实测 0.0397 | **外推 1.72** | 实测 0.0051 | **≈1.77 ms** | 512 MB | ≈0.52 GB | ~200 |
| 4096 (N=4) | 实测 0.0186 | 实测 0.0670 | **外推 3.43** | 实测 0.0080 | **≈3.53 ms** | 1.0 GB | ≈1.02 GB | ~400 |
| 8192 (N=8) | 实测 0.0369 | 实测 0.1306 | **实测 6.93** | 实测 0.0258 | **≈7.12 ms** | 2.0 GB | ≈2.03 GB | 800（1.00） |
| 16384 (N=16) | 实测 0.0702 | 实测 0.2532 | **实测 13.85** | 实测 0.0481 | **≈14.2 ms** | 4.0 GB | ≈4.05 GB | ≥800（外推~1600） |

**读法（给所有者）**：
- **延迟曲线是直线**：每翻一倍 D，单拍线性翻倍（0.89→1.77→3.53→7.12→14.2ms）。这就是他说的"维度更多→思考更慢"，**实测成立**。
- **但斜率 100% 来自检索**。把检索拿掉，D=16384 的其余三项仅 0.38ms（绑+捆+读写），D=1024 时三项 0.033ms——绝对差 0.35ms，而检索从 0.86 涨到 13.9ms。
- **显存曲线也是直线**：码本 M·D·4，D=16384 时 4GB，占满预算一半。
- **上下界**：检索延迟下界 = M·D·1/BW（纯位打包 1-bit 理论 1/32）；上界 = 上表 ×2（RVC 共存带宽争用最坏情形，未实测，属风险预留）。

**模型外的天花板（诚实）**：D 继续翻到 32768/65536 时，码本显存 8GB/16GB → **爆**。所以"线性扩维"的硬墙是**显存**，不是延迟。
若把词表缩到 M=8192：D=131072（N=128）时码本仍 4GB、单拍 13.9ms，**线性路能摸到单 bundle 容量 ~6.5×10³**——但代价是词表被挤到 8192 码位。

## 4. 【硬要求 2】可行 N 上限

### 4.1 约束不等式

```
延迟约束：R · M·D·b / BW  ≤  L_budget
显存约束：M·D·b           ≤  B_AHI · 1e9        （B_AHI = 8GB）
容量约束：0.05·D          ≥  需要的单拍同时码位
词表约束：M               ≥  语言本体 ~ 10³~10⁴
```

### 4.2 单引擎（R=1 检索/拍，Q=1）

| 场景 | 预算 L | 约束 | **N 上限（M=65536）** | **N 上限（M=8192）** |
|---|---|---|---|---|
| 思维拍 | 50 ms | 50ms > 13.9ms ⇒ **显存绑定** | **N=16**（D=16384，4GB，13.9ms） | **N=128**（D=131072，4GB，13.9ms） |
| 手轨迹 | 16 ms | 16ms ⇒ 延迟绑定 | **N=8**（D=8192，2GB，6.9ms）；N=16 为极限(87%预算) | **N=64**（D=65536，2GB，6.9ms） |
| 发声首字 | 300 ms | 300ms ⇒ 不绑定 | N=128 也不受限（13.9ms ≪ 300ms） | 同左（受显存限） |

**单引擎结论**：**思维拍的正确上限是 N=16（全词表）/ N=128（精简词表）**，卡在显存；手是 N=8/N=64，卡在延迟。R 若增到 4 次检索/拍，N 上限再降一半（思维 N=8，手 N=4）。

### 4.3 多引擎并发（C 引擎共享一张卡、共享只读码本）

- **显存不随 C 倍增**（码本只读共享，仅工作区/临时各引擎私有，V_tmp·C 仍很小）。
- **延迟不随 C 增长（当 C≤32）**：项目先例"多引擎吞吐形 GPU 批量 **63–81×**"与本次实测"Q 1→32 每查询降 **24×**"同源——**把 C 个引擎的检索合并成一个 Q=C 的批量 GEMM，码本只搬一次**。
- 因此 **多引擎并发的 N 上限 = 单引擎 N 上限**（16 / 128），但**吞吐提升 ~24×（C≤32）**；C>32 后退回算力线性区。

**一句话**：**扩维吃的是每引擎的延迟预算（N≤16 全词表）；并发引擎吃的是批量摊销，两者正交，可以同时要。**

## 5. 【硬要求 3】非线性逃逸路径（逐条量化收益）

> 目标：把 `O(M·D)` 的检索成本掰弯，在**容量上升时让常驻延迟不变或次线性增长**。

### E5（最有效）多分辨率 / 按需展开 —— 唯一能"容量↑而常驻延迟不变"的路

**结构**：常驻一张**粗码本**（低分辨率 D_c，如 1024）；细码不常驻，由粗码经固定随机投影 `P (D_f×D_c)` 按需生成：`细码 = sign(P @ 粗码)`。

**算法**：① 粗码本扫描 → 每查询取 top-k 粗候选；② 候选**去重**成唯一集 U；③ `index_select` 一次性取细码；④ 单次 GEMM 打分；⑤ 掩码取每查询 top-1。

**收益（实测 + 带宽推算）**：
- 常驻延迟 **0.129ms**（M=8192, D_c=1024），**与细码分辨率 D_f 完全无关**；
- 细码分辨率升到 8192 时，全细码扫要 **0.780ms**；两阶段**带宽**只需 32MB(粗)+8MB(候选)=40MB → **6.4× 省带宽**；
- 实测端到端 0.560ms（K=8）= **1.4×**，**未达 6.4×**——差额被小算子启动开销（unique/index_select/mask ~4 个 kernel）吃掉；**用 CUDA Graph 捕获或融合后预期恢复 4–6×**（诚实：此句为推算，需实测）。
- 容量：细码层单 bundle 容量 = 0.05·D_f，**随 D_f 任意升**；常驻粗码层容量仍 0.05·D_c 不变。

**这条直接回答所有者**："容量↑但常驻延迟不变"**成立**——条件是常驻只放粗码，细码按需算；代价是 top-1 从粗码 top-k 里选，K=8 时一致率 0.81、K=32 时 0.94（要保真 0.95 需 K≥32，但 K 大则带宽省得少）。

### E1 稀疏码 + 倒排索引 —— 把 O(M·D) 降到 O(候选数 · k)

**结构**：码只存 k 个非零位（索引+符号对）；建**位置桶倒排**（每个维度位 → 命中码列表）；查询时只扫与查询非零位命中的桶取并集做候选。

**收益**：
- **扫描量**：实测 D=4096, M=65536 全扫 3.25ms → 候选 4096 时 **0.252ms = 12.9×**（真测）；
- **显存**：k=64, D=4096 时存 (64×4B 索引 + 64bit 符号) ≈ 264B vs 稠密 16384B → **62×**；
- **保真代价**：稀疏码余弦与稠密码同分布（同为 ±1 随机），容量律不变，但倒排候选集需覆盖真值——理论候选召回率 <1，需 k 足够大（k/D ≥ 3–5%）；
- **GPU 现实**：稀疏 GEMM 在 k/D 低时才快，桶并集用 `index_select`+稠密小 GEMM 更稳（实测路线）。**净收益给 8–13×。**

### E3 驻留 + 批量摊销 —— 项目已验，直接复用

- 项目先例：**驻留态 GPU 弛豫 12×、M读 50×、lookahead 26×**（`bench_gpu.py` / `meeting16` §3）；多引擎吞吐形 **63–81×**；镜像进出模式慢 3–4×（传输主导）。
- 本次实测补充：**查询批 Q 1→32 每查询 24×**。
- **合起来**：把 AHI 热路径做成"码本常驻 + 每拍把所有引擎/器官的查询并成一个 Q≤32 的批量" → 单查询等效成本 **降 30–70×**（= 24× 批摊销 × ~2–3× 免镜像往返）。
- **前提**：必须有 ≥32 个并发查询可供合并（多引擎/多候选/多槽同时检索）。单引擎单查询享不到。

### E2 分块 / 分片 —— 只算"脏块"

- 把 D 切块（如 16 块 × D/16），**只重算本拍变化的块**。若每拍仅 10% 维度变化 → 受影响算子 **~10×**。
- 模态分片：把各模态码本分段常驻，热段在 L2 命中——实测捆绑在 L2 内带宽 ~500GB/s（0.0242ms 对应 12.6MB/3e11 的 1.6×），**热段命中省 ~1.6×** 带宽。
- 代价：块间耦合（跨块绑定）需同步；对"低频粗码常驻"（E5 的粗层）适配最好。

### E4 预计算 / 查表 —— 冻结角色码与绑定结果

- 角色码（self/agent/intent…）**运行期不变** → 角色⊗填充的**填充位**可预投影；模板句的绑定结果可缓存。
- 命中率 c 时成本 ×(1−0.9c)：c=60% → **2.7×**；c=80% → **~5×**。
- 显存代价 = 缓存条目数 × D × b；建议 LRU 上限 256 条（256×D×4，D=16384 时 16MB，可忽略）。

### E0 量化（附赠，零风险）

- fp16 码本 **实测 2.3×**（0.870→0.378ms）；int8 预期 ~4×；1-bit 打包理论 **32×**（需 XOR-popcount 自定义 kernel，torch 无现成，暂不承诺）。
- **建议默认 fp16 码本**：立即把 §3 表的显存与延迟各减半，N 上限线上移一档（思维 N=16→32 全词表）。

### 路径汇总（收益 vs 代价）

| 路径 | 量化收益 | 主要代价 | 证据等级 |
|---|---|---|---|
| **E5 多分辨率按需展开** | **6.4× 带宽（实测 1.4×，融合后 4–6×）**；常驻延迟与 D_f 解耦 | 保真降（K=32→0.94）；实现复杂度 | 实测+推算 |
| E1 稀疏+倒排 | **8–13× 扫描**；显存 62× | 桶召回有损；GPU 稀疏实现 | 实测锚点 |
| E3 驻留+批量摊销 | **30–70×** 单查询等效 | 需 ≥32 并发查询 | 项目实测+本次实测 |
| E0 fp16 量化 | **2.3×**（延迟与显存同降） | 无（保真损失可忽略） | 实测 |
| E4 预计算/查表 | 2.7–5× | 缓存显存（可忽略） | 估算 |
| E2 分块/分片 | ~10×（脏块比例） | 跨块同步 | 估算 |

**最有效的一条（唯一答案）**：**E5 多分辨率按需展开**——只有它把"容量"与"常驻延迟"**解耦**，其余路径都只是把直线斜率压低（仍线性），E5 是把曲线**掰弯**。

## 6. 【硬要求 4】"算力换容量"刻度表（所有者最想要的形式）

**规则**：可行域由 `M·D ≤ min( B·1e9/b , L·BW/(R·b) )` 决定；给 X GB + Y ms，即可得多少**可寻址码位 M** 与**同时活跃容量 0.05·D**。

### 6.1 显存刻度（AHI 自有预算 B，fp32）

| AHI 显存 B | 可行 M·D 上界 | D=1024→M | D=4096→M | D=16384→M | D=65536→M | 同时活跃容量(0.05D) |
|---|---|---|---|---|---|---|
| 2 GB | 5.0×10⁸ | 488 k | 122 k | 30 k | 7.6 k | 51 → 3277 |
| 4 GB | 1.0×10⁹ | 977 k | 244 k | 61 k | 15 k | 51 → 3277 |
| **8 GB** | **2.0×10⁹** | **1.95 M** | **488 k** | **122 k** | **30 k** | **51 → 3277** |
| 8 GB + fp16 | 4.0×10⁹ | 3.9 M | 977 k | 244 k | 61 k | 51 → 3277 |

> "M 列" = 该显存下、该维度能装下的**码本码位数**（可寻址码位数）。"同时活跃容量" = 单个工作区 bundle 能同时不塌地持有的码位（0.05·D，D 对应最左→最右列）。

### 6.2 延迟刻度（M=65536 全词表，R=1）

| 预算 L | 允许 M·D | D 上限 | 对应单拍 | 对应码本显存 |
|---|---|---|---|---|
| 16 ms（手） | 1.24×10⁹ | **D=18900** | 15.9 ms | 4.6 GB（fp32，偏大）→ fp16 2.3GB |
| 50 ms（思维） | 3.88×10⁹ | **D=59200** | 47 ms | 14 GB ❌ 显存先爆 |
| 300 ms（发声） | 2.3×10¹⁰ | 不限 | — | — |

### 6.3 一句话刻度（给所有者的直答）

> **"你有 8GB 显存 + 50ms 思维拍" → 全词表（M=65536）可上 N=16（D=16384、单拍 13.9ms、码本 4GB），单拍同时活跃 ~1600 码位；若接受精简词表（M=8192），可上 N=128（D=131072、13.9ms、4GB），单拍同时活跃 ~6500 码位。**
> **再多要容量，不是靠继续扩 D（显存会爆在 D≈32768/65536），而是靠 E5/E1/E3：粗码常驻 + 细码按需 + 稀疏倒排 + 批量摊销，把这些数字再抬 4–10×。**

## 8. 【硬要求 6】诚实边界

**有实测支撑的结论**（本机 RTX 3080 Laptop，隔离态）：
- 检索延迟 ∝ M·D，有效带宽 3.3 µs/MB ≈ 310 GB/s（三档规模一致）；
- 绑定/捆绑/工作区为微秒级、与检索差 2–3 个数量级；
- Q 1→32 批量摊销 24×；fp16 预转换 2.3×；
- 单 bundle 容量律 0.05–0.1·D（D=1024→100、D=16384→800+）；
- 多分辨率两阶段实测 1.4×（K=8，含算子启动开销），保真 0.81/0.94。

**纸面推演（未实测，标注为外推/估算）**：
- D≥2048 的检索延迟为按 M·D 线性外推（256MB@3.35µs/MB、256MB@3.4µs/MB 两点锚定；外推可信但非实测）；
- E5 "融合后 4–6×"为带宽推算，实测仅 1.4×（launch 开销主导），**必须用 CUDA Graph / 融合 kernel 复测后才能兑现**；
- E1 稀疏收益 8–13× 中，仅"候选裁剪 12.9×"为实测；显存 62×、桶召回率为估算；
- E2/E4 收益为估算；
- 上表所有 ±2× 上界（RVC 争用最坏情形）未实测。

**未覆盖 / 做不到的**：
- **RVC 共存干扰未实测**：RVC 训练会抢 SM、抢带宽、抢显存；本文全部数字是隔离态。**建议在 RVC 训练运行时重跑 §1.1**，预期检索延迟劣化 1.5–2×。
- **写/维护拍未量化**：M 实例驻留的增量同步（项目 #204/#206 有先例）不在本文口径内。
- **声带合成是另一条独立瓶颈**：`声带.py::合成波形` 逐样本 Python 循环（3s 语音 ≈48000 迭代），与扩维无关；发声首字 300ms 的达标与否取决于它，不取决于 D。
- **本文不解决容量数学**：为什么 0.05·D 是上限、稀疏/层次码能否把 0.05 提到 0.3，属 01 号专家；本文只保证"若你把容量律提到某个 K，我能在预算内把它算完"。
- **禁 Transformer 边界下无更快的检索器**：本文所有加速都是 HDC 原生算子（矩阵乘/按位/索引），未引入任何神经组件。

## 附录 A · 三张速查卡

**卡 1 · 代价主式**
```
T_retr[ms] ≈ M · D · b / 3.1e8      （Q ≤ 32，带宽绑定）
T_other   ≈ D · 4e-5 ms             （绑定+捆绑+工作区，可忽略）
V[bytes]  ≈ M · D · b               （显存，码本主导）
```

**卡 2 · 约束三角**
```
显存 ≤ 8GB       →  M·D·b ≤ 2e9（fp32）
思维拍 ≤ 50ms    →  R·M·D·b ≤ 3.9e9（R=1）
手 ≤ 16ms        →  R·M·D·b ≤ 1.24e9（R=1）
⇒ 1 次检索/拍：显存绑定；R≥2：延迟绑定
```
