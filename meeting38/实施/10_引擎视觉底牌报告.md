## 1. 引擎现有表示原语（底牌清单，源码核对）

| 原语 | 位置 | 干什么 | 对视觉的承载力 |
|---|---|---|---|
| **`编码器.特征码(向量)`** | 共存态.py:106-118 | **任意实数特征 → 固定随机投影 → 1024 双极**（投影阵按输入维度缓存，永不训练） | ★**这是引擎的"眼睛入口"**：任何实数特征向量都能进 HDC，**无模型、无梯度、无 Transformer** |
| `编码器.字码/文本码` | 共存态.py:88-104 | 字→双极；文本→字袋多数表决 | 承载**系统自报文字**（非 OCR） |
| `编码器.绑(移位)` | 共存态.py:121-129 | 按位乘 + 循环移位（位置绑定） | 表达"哪个属性/哪个位置" |
| `编码器.束` | 共存态.py:131-138 | 多数表决叠加 | 多特征合成一个元素码 |
| `编码器.相似/批相似` | 共存态.py:140-159 | 余弦（GPU 常驻） | 检索/聚类 |
| `数轴`（档位链+双轴） | 声带.py:47-99 | 连续量→256 档，相邻档 cos 线性衰减 | 颜色/位置/强度等**连续量**的原生编码 |
| `lang_codec.编码` | lang_codec.py:53-67 | 字符 bigram + 位置绑定 → 1024 双极（顺序敏感） | 文本顺序信息 |
| **`语义.功能签名`** | 语义.py:244-295 | `签名 = 束(新增码 ⊕ 消失码 ⊕ 变化码)`——**"这个元素是什么"由它自己亲历的点击结果决定** | ★**这是"知道"的机制本体**（名字、长相都不参与） |

| `语义.叠加支配` | 语义.py:150-219 | 谁接住点击，**由真实点击裁决累积**，初始如实"未知" | 交互实证 |
| `语义._重聚类` | 语义.py:298-333 | 功能签名余弦聚类 → **异名同效归并、同名异效分开** | 语义泛化（无需标注） |
| FSW 内核 / 情感因子层 / EFE | 实施/fsw_kernel.py、情感因子层.py、发声动作与EFE.py | 长时库检索+精排、因子化编码、动作选择（步 0–2b 已验收） | 元素/经历可入库检索；动作选择 |

**一句话**：引擎具备"任意实数特征→HDC"（特征码）与"亲历交互→语义"（功能签名）两条原生通路；
它缺的从来不是表示能力，而是**喂给它的东西来自外挂模型**（YOLO 框 + OCR 字）。

## 2. 现有视觉链的实底与病灶

`器官_眼.py` 现状：截屏(mss) → **YOLO 框**(`:144`) → **OCR 识字**(`:224`) → 写视觉槽
（句柄/框/心/字/主色/形状/置信）→ `语义.py` 事后按"点击有没有反应"猜功能。

- 病灶一（所有者已点名）：**YOLO/OCR 是外挂模型当器官**，只"框出来/认字"，不"知道内容"。
- 病灶二：元素码（`语义._元素码` :222-242）里的"字"来自 OCR；OCR 一禁，**文字通道就断了**。
- 已存在的资产：`器官_眼._普查`（:156-179，Canny 边缘 + 连通域）**已经是一条非模型路径**，
  现在只当"YOLO 失败时的降级"。**它是原生视觉现成的起点。**

## 3. 缺口（Gap 清单）——只两条

| # | 缺口 | 说明 |
|---|---|---|
| G1 | **像素/区域 → 实数特征向量** 的非模型提取器 | 引擎入口（特征码）要的是实数向量；目前没人做"像素→向量"这一段（YOLO 直接给了框，跳过了） |
| G2 | **文字的非 OCR 来源** | 元素码与容器树命名都要"字"；OCR 禁用后必须换源 |

## 4. 候选手段（可行性已实测核查，全部不撞红线）

**G1：非模型 CV 特征提取（`cv2` 已在，实测 OK）**
- 颜色：RGB/HSV 直方图（分箱）
- 边缘/纹理：Canny 边缘密度、局部方差、梯度方向直方图（HOG-lite）
- 形状：连通域宽高比、填充率、**Hu 矩**（旋转/尺度不变）
- 布局：框的 x/y/w/h 相对屏幕归一化（**已有**，语义._元素码 在用）
- 全部是确定性算子，零梯度、零模型 → 交给 `编码器.特征码` → 双极码。

**G2：文字的系统自报通道（实测可用，非 OCR）**

| 通道 | 依赖 | 实测 |
|---|---|---|
| **Windows UI Automation**（控件名/角色/值/状态） | `comtypes`（**已有**）+ UIAutomationCore COM | 可直接调，**无需** uiautomation/pywinauto 包（这两个缺失但不需要） |
| 窗口标题 | `win32gui`/`win32api`（**已有**） | **项目已有多处先例**：AHI躯体.py:47、AHI操作WPS.py:65、浏览器体.py:85 等用 `GetWindowTextW` |
| 剪贴板 | win32clipboard | 可用 |
| 网页 DOM | Edge/浏览器（项目已有浏览器体） | 可用 |

> 这些是**系统自报的结构事实**（不是识别出来的），正是"联动式"里"联动"的另一半：
> **向系统要它自己知道的，而不是从像素猜。**

## 5. 「联动式视觉」的三层落地映射（与既有资产对接）

```
① 看（非模型）   截屏 + cv2 特征（颜色/边缘/形状/纹理）→ 编码器.特征码 → 元素双极码
                 复用 器官_眼._普查 骨架，从"降级"升为主路径
        ↓ 联动 A：与系统结构对齐（同一元素 = 像素区 ∩ 系统控件）
② 认（非 OCR）   向系统要结构：UIA 控件名/角色/值 + 窗口标题 + 剪贴板
                 → 编码器.文本码 → 与①按位绑定（语义._元素码 的手法，已有）
        ↓ 联动 B：与交互历史对齐
③ 知（非模型）   语义.py 功能签名（亲历点击→新增⊕消失⊕变化）→ 功能词聚类
                 + FSW 长时库检索（这是什么/我以前在哪见过它/它和我的关系）
        ↓ 联动 C：与自我/动作闭环（步 3b 的事件槽 + 自我槽已就位）
④ 用             EFE 选动作（步 2b 已验收）→ 手/嘴执行 → 结果回流 → 回到③
```

**关键洞察**：这三层**没有一层需要新范式**。①用 cv2（经典 CV），②用系统 API（自报），
③用项目已验收的 HDC 语义/检索机制。"原生"在这里的含义 = **感知与理解都由引擎自己的算子构成，
外部只提供事实（像素、系统结构），不提供判断（模型标签）**。

## 6. 诚实边界（不粉饰）

1. **"原生像素级理解"仍未解决**——本报告不声称打通了"从像素直接理解语义"。它给的是：
   用非模型特征 + 系统结构 + 交互实证**绕开**那条未打通的硬路，同时**不退回**模型识别。
2. **系统结构通道有覆盖率上限**：UIA 只对有可访问性支持的应用有效（WPS/Office/浏览器好，
   自绘 UI（游戏、部分 Electron、canvas）拿不到控件树）——那类只能靠①的 CV 特征 + ③的交互实证。
3. **文字仍可能缺失**：纯图形界面（图标按钮）无字可读，此时靠③的交互功能签名——这正是
   `语义.py` 的设计意图（**名字长相都不参与判断**），所以不是致命伤，但"知道"会更慢（需亲历）。
4. **性能**：CV 特征 + UIA 遍历都要实测延迟；UIA 遍历在深树上可能慢，需按需/缓存（参照
   现有 OCR 缓存与容器树的按需策略）。
5. **本文档是研究，不是方案**。是否开工、按哪条路，待所有者裁决。
